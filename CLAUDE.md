# LuckySort

Procedural robotic color-and-size stacking benchmark built on **Lucky Engine**
(C# scripting, ECS, MuJoCo physics, RobotControllerComponent + motion-graph IK,
Observer recording). Intended as an interview demo of engine/robotics systems design.

The full spec is in `docs/LuckySort_Idea_Plan.md`. Read the relevant section before
starting any stage.

## Rules (from plan §28)

1. **Inspect before implementing.** Never invent Lucky APIs. Confirm every method
   against the installed engine version or the docs at https://docs.luckyrobots.com/stable/.
   Record confirmed APIs in `docs/LUCKY_API_NOTES.md`.
2. **Incremental.** Robot movement → pick/place → single stack → multiple colors →
   generation → evaluation → randomization → recording → benchmark → polish.
   Don't move on until the current milestone is reliable.
3. **Modular.** Keep Generation, Planning, Robot Control, State Machine, Evaluation,
   Episodes, Recording and UI in separate scripts/folders (plan §23).
4. **Planner uses task metadata; evaluator inspects physical state.** Never let the
   evaluator trust the planner.
5. **Determinism.** All randomness flows from an explicit seed. Same seed → same task.
6. **Fixed timestep.** No `Thread.Sleep` or wall-clock delays; use sim time/state
   conditions and the Time Manager runners.
7. **No teleporting** the robot or objects during normal operation; use IK + gripper
   on real MuJoCo rigid bodies.
8. **Don't over-engineer.** Tier 1–2 stability before Tier 3–4 features (plan §29).

- `docs/` — plan and API notes (read `LUCKY_API_NOTES.md` before touching engine code)
- `LuckySortStack/` — the Lucky Engine project (LuckyEngine 2026.1.2, Franka Panda)
  - `Assets/Scenes/Main.hscene` — start scene
  - `Assets/Scripts/Client/Source/` — C# scripts (namespace `LuckySortStack.*`)
    - `Core/`, `Benchmark/`, `Generation/`, `Planning/`, `StateMachine/`, `Evaluation/`, `Recording/`, `Presentation/`, `Robot/Abstractions/` — **engine-independent**
      (System.Numerics only, no `Hazel`), unit-tested
    - `Robot/PandaManipulator.cs` — `IManipulator` over the motion graph + `actuator8`
    - `Episodes/EpisodeManager.cs` — scene-side: reads workspace, generates task, lays out pool,
      plans and runs the `TaskStateMachine`, evaluates, records; loops episodes in benchmark mode. Exactly one per
      scene (extra instances disable themselves)
    - `Episodes/SceneWorldState.cs` — `IWorldState` over the pool entities
    - `Episodes/ObserverSession.cs` — drives Lucky's Observer (episode boundaries, per-pick labels)
    - `Episodes/SceneResetter.cs` — in-Play reset between benchmark episodes (MuJoCo reset + measured qpos writes)
    - Episode records are written to `LuckySortStack/Recordings/<session>/` (gitignored)
    - The Observer's own dataset goes to `LuckySortStack/DataSessions/session_<time>/` (gitignored)
    - `UI/DebugOverlay.cs` — on-screen overlay (text entities parented to the camera) + DebugRenderer world markers
    - `UI/PresentationCamera.cs` — demo camera views (C) driving the scene camera
    - `Panda.cs` — Stage 0/1 smoke test (off unless `RunSmokeTest`)
  - `Assets/ContentVault/Robots/Panda/` — MJCF + motion graph
- `Tools/SceneBuilder/` — generates the workspace (mat, stack markers, object pool, materials)
  into `Main.hscene`. All generated entities are tagged `LS_*` with deterministic IDs; re-running
  replaces them. Layout constants live in its `Layout.Default`.
  **The Lucky editor must be closed** when it runs (editor autosave overwrites the scene).
  Run: `dotnet run --project Tools/SceneBuilder -- LuckySortStack`
- `Tests/LuckySort.Core.Tests/` — xunit tests compiling the engine-independent folders directly.
  `FakeSim` is a kinematic stand-in for arm + physics (with fault injection) so whole episodes
  run offline.
  Run: `dotnet test Tests/LuckySort.Core.Tests`. `GoldenSeedIsUnchanged` pins seed 1234's
  fingerprint; changing it means every recorded seed now maps to a different task.
- `Python/` — optional gRPC experiment runner (late stage only)

## Workspace layout (metres, Y-up, robot base at origin, +X forward)

- Workspace mat: x 0.25–0.75, z −0.45–0.45, top at y = 0.01
- Object pool: 4 colors (Red, Blue, Green, Yellow) × 4 cube sizes (Large 60, Medium 50,
  Small 40, Tiny 30 mm); tags `LS_Obj_<Color>_<Size>`; spawn region z < 0
- Stack targets: `LS_StackTarget_<Color>` at (0.40, 0.18) Red, (0.55, 0.18) Blue,
  (0.40, 0.33) Green, (0.55, 0.33) Yellow (x, z)

## Key engine facts (details in docs/LUCKY_API_NOTES.md)

- World is Y-up; IK targets are world metres, orientation in degrees.
- Gripper = actuator `actuator8`, 255 open / 0 closed; set `.IK = false` first.
- One `SetInputTrigger` per motion step; each trigger cancels the in-flight move.
- Manipulables must be MuJoCo bodies. Runtime spawning is undocumented, so use a pre-authored object pool.
- `Hazel.Random` can't be seeded; use `System.Random(seed)` (its seeded algorithm is stable across .NET versions).
- Keep `Core/` and `Generation/` free of `Hazel` types so they stay testable; convert at the
  boundary (`EpisodeManager` aliases `System.Numerics` as `Num`).
